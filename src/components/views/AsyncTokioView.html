Appendix 02 • Concurrency Deep Dive

Node.js libuv vs Tokio Multi-Threaded Runtime

Understanding poll-based futures, work-stealing executors, and why async Rust achieves sub-millisecond p99 latencies.

🟢 Node.js (libuv)

  • Single-threaded: Javascript executes on exactly one thread.
  • Push-based: Callbacks pushed to microtask/macrotask queues.
  • Event loop blocking: Heavy CPU computations freeze all incoming HTTP requests.
  • Promises: Eager evaluation (starts executing immediately upon instantiation).

🦀 Rust (Tokio)

  • Multi-threaded: Work-stealing scheduler across all physical CPU cores.
  • Pull-based: Futures are polled only when awakened by Waker.
  • CPU isolation: CPU tasks run cleanly on tokio::task::spawn_blocking or Rayon.
  • Futures: Lazy evaluation (does nothing until polled with .await).

The Cardinal Rule of Tokio

NEVER CALL SYNCHRONOUS BLOCKING CODE INSIDE AN ASYNC FUNCTION!
std::thread::sleep or synchronous file I/O blocks the OS thread assigned to the Tokio worker, stalling hundreds of concurrent HTTP futures!

Always use non-blocking equivalents: tokio::time::sleep and tokio::fs, or offload with tokio::task::spawn_blocking.

Cooperative Multitasking & tokio::task::yield_now()

Node.js developers frequently use setImmediate() to break up long-running computation loops so the event loop can service I/O. In Tokio, tasks run cooperatively without preemption on worker OS threads. If a task executes a CPU-heavy or tight iterative loop without hitting an .await point, it starves other tasks assigned to the same worker thread.

The Solution: Call tokio::task::yield_now().await inside long-running async loops. This yields back to the Tokio scheduler, placing the current task at the back of the local run-queue. 
use tokio::task;

async fn process_large_dataset(chunks: Vec<Chunk>) {
    for (i, chunk) in chunks.into_iter().enumerate() {
        process_chunk(chunk);

        // Cooperatively yield execution every 100 iterations:
        if i % 100 == 0 {
            task::yield_now().await;
        }
    }
}

Note: Tokio also features an automatic internal "co-op budget" (defaulting to 128 poll iterations) for standard Tokio I/O drivers, but explicit loops require manual yields or spawn_blocking.

tokio::select! & Cancellation Safety

In JavaScript, Promise.race([a, b]) allows the loser promise to continue executing in the background until fulfillment. In Tokio, tokio::select! employs destructive cancellation: whichever branch does not complete is dropped immediately, running the future's Drop destructor.

A future is cancellation-safe if dropping it before completion does not cause corrupted state or dropped data when polled again or on retry.

mpsc::Receiver::recv

❌ Cancellation Unsafe AsyncReadExt::read_exact
AsyncWriteExt::write_all

Idiomatic Workaround for Unsafe Operations in select!:

Keep the future pinned across iterations or use a loop over AsyncReadExt::read rather than read_exact:

// Pin the operation OUTSIDE the select loop to prevent dropping progress:
let mut write_fut = Box::pin(writer.write_all(&payload));

tokio::select! {
    res = &mut write_fut => { /* handle completion */ }
    _ = cancel_rx.changed() => { /* handle abort safely without dropping partial state */ }
}
