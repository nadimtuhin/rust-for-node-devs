Appendix 05 • Containerization

Production Multi-Stage Dockerfile & Binary Optimization

Build static binaries with cargo-chef caching, symbol stripping, MUSL cross-compilation, and distroless/scratch runtime containers.

Key takeaways

  • A multi-stage Dockerfile compiles a Rust service in a full rust image and copies only the finished binary into a small runtime image, so the compiler and build cache never ship to production.
  • cargo-chef caches dependency compilation in its own Docker layer: cargo chef prepare writes a recipe of the dependency graph and cargo chef cook builds only the dependencies, so source-only changes skip that layer.
  • A Rust binary built against glibc on Debian 13 (trixie) runs on gcr.io/distroless/cc-debian13, which provides glibc, libgcc, CA certificates and a nonroot user but no shell or package manager.
  • Building for x86_64-unknown-linux-musl produces a statically linked binary that can run in an empty scratch image, provided you also copy in CA certificates if the service makes TLS calls.
  • For comparison, the official node:22-slim image is about 80 MB compressed on Docker Hub (amd64, October 2026) before any application code or node_modules are added.

1. Multi-Stage Dockerfile with cargo-chef (glibc + Distroless)

This follows the pattern from the cargo-chef README: dependencies are compiled in a cached layer, then the binary is stripped and copied into Google Distroless. The builder and the runtime (cc-debian13) are both Debian 13 (trixie), so they share the same glibc version, which avoids "GLIBC_x.y not found" errors at startup. latest-rust-1-trixie tracks the newest stable Rust; pin a specific tag such as latest-rust-1.NN-trixie for reproducible builds.

# Stage 1: base image with Rust and cargo-chef preinstalled
FROM lukemathwalker/cargo-chef:latest-rust-1-trixie AS chef
WORKDIR /app

# Stage 2: compute the dependency recipe
FROM chef AS planner
COPY . .
RUN cargo chef prepare --recipe-path recipe.json

# Stage 3: build dependencies (cached layer), then the app
FROM chef AS builder
COPY --from=planner /app/recipe.json recipe.json
RUN cargo chef cook --release --recipe-path recipe.json
COPY . .
RUN cargo build --release --bin server
# Remove the symbol table (same effect as strip = true in Cargo.toml)
RUN strip /app/target/release/server

# Stage 4: minimal runtime: glibc + libgcc + CA certs, no shell
FROM gcr.io/distroless/cc-debian13:nonroot
WORKDIR /app
COPY --from=builder /app/target/release/server /app/server
USER nonroot:nonroot
EXPOSE 3000
ENTRYPOINT ["/app/server"]

2. Declarative Stripping in Cargo.toml

Instead of invoking the external strip utility in Docker, you can have Cargo strip symbols and enable link-time optimization through [profile.release]. Since Rust 1.77, release builds already strip debuginfo by default; strip = true also removes the symbol table. Check the result with ls -lh target/release/server rather than relying on a fixed percentage:

# Cargo.toml
[profile.release]
opt-level = 3          # Release default; use "s" or "z" to optimize for size
lto = true             # Full ("fat") Link-Time Optimization across crates
codegen-units = 1      # Larger optimization scope at the cost of compile time
strip = true           # Strip symbols and debuginfo from the output binary
panic = "abort"        # No unwinding tables; any panic ends the whole process

3. Static Binaries with MUSL (FROM scratch)

Rust's *-linux-gnu targets dynamically link to GNU libc (glibc). The *-linux-musl targets link musl libc statically by default, producing an executable with no shared-library dependencies that can run in an empty scratch image. scratch also has no CA certificates, timezone data or user database, so copy in what your service needs.

Common Target Triplets:

  • x86_64-unknown-linux-musl: 64-bit Linux (Intel/AMD)
  • aarch64-unknown-linux-musl: 64-bit Linux (ARM64 / AWS Graviton / Docker on Apple Silicon)

MUSL multi-stage Dockerfile:

# Build a statically linked binary for the musl target on Debian
FROM rust:1-trixie AS builder
# musl-tools provides musl-gcc for crates that compile C code
RUN apt-get update && apt-get install -y --no-install-recommends musl-tools musl-dev && rm -rf /var/lib/apt/lists/*
WORKDIR /app

RUN rustup target add x86_64-unknown-linux-musl

COPY Cargo.toml Cargo.lock ./
COPY src ./src
RUN cargo build --release --target x86_64-unknown-linux-musl --bin server

# Empty base image: only the binary and the CA bundle
FROM scratch
COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/ca-certificates.crt
COPY --from=builder /app/target/x86_64-unknown-linux-musl/release/server /server
# Numeric UID: scratch has no /etc/passwd, and the default would be root
USER 10001:10001
EXPOSE 3000
ENTRYPOINT ["/server"]
Note on OpenSSL & TLS: Linking OpenSSL statically against musl is awkward, so prefer a rustls-based TLS stack (the default in reqwest 0.13) over native-tls / openssl. Either way the binary still needs trusted root certificates: copy the CA bundle as shown above, or compile them in with the webpki-roots crate.
Note on allocator performance: musl's built-in malloc is simpler than glibc's and can be slower under multi-threaded allocation load. Services built for musl often set a global allocator such as mimalloc or tikv-jemallocator; benchmark your own workload before and after.

Frequently asked questions

Why are Rust Docker builds so slow compared to npm ci?
Rust compiles every dependency from source, and a plain COPY . . followed by cargo build invalidates that work on every source change. cargo-chef fixes this by building dependencies from a recipe file in a separate layer that Docker reuses until Cargo.toml or Cargo.lock change. BuildKit cache mounts for ~/.cargo/registry and target/ are an alternative.
Which base image should I use to run a Rust binary?
For a glibc build from a Debian 13 (trixie) builder, use gcr.io/distroless/cc-debian13:nonroot, which includes glibc, libgcc and CA certificates and runs as a non-root user. For a static musl build, scratch works if you copy in CA certificates yourself. Use debian:trixie-slim instead if you need a shell for debugging.
Do I need node_modules or a runtime in the final Rust image?
No. Rust crates are compiled into the executable, so the runtime image needs only the binary plus any system libraries it links dynamically (glibc for -gnu targets, nothing for static musl builds). There is no interpreter or package directory to copy.
Why does my Rust binary fail with "GLIBC_2.xx not found" in Docker?
The binary was built against a newer glibc than the runtime image provides. Build and run on the same Debian release, for example a -trixie builder with distroless/cc-debian13, or build for a musl target to remove the glibc dependency entirely.
Should I use musl or glibc for a Rust container?
glibc on a distroless image is the simpler default and avoids musl's slower allocator under multi-threaded load. Choose musl when you want a fully static binary for scratch or for running on any Linux distribution, and pair it with rustls and a faster allocator such as mimalloc.
