Appendix 03 • Package Management

Cargo vs npm / pnpm

Additive feature flags, duplicate dependency handling without node_modules, workspace inheritance, pre-1.0 SemVer rules, and release profiles.

1. Rosetta Stone: Core CLI Workflow

Node.js / npm Rust / Cargo What it does
npm init -y cargo init / cargo new <name> Initialize new project
npm install <pkg> cargo add <crate> Add dependency to Cargo.toml
npx tsc --noEmit cargo check Fast type & borrow check without codegen
npm run build cargo build --release Compile optimized machine code
npm test cargo test Run unit & integration tests
npx eslint . cargo clippy Run strict static linter

2. How Cargo Solves the node_modules Problem

In Node.js, duplicate packages often lead to massive nested node_modules and runtime collisions (prototype pollution). Cargo compiles external crates once into target cache. If two dependencies require different major versions (e.g. serde 1.0 and serde 0.9), Cargo mangles the symbols and compiles both side-by-side with zero collisions.

3. Additive Feature Flags

In Rust, crate capabilities are gated behind compile-time feature flags. Features are strictly additive: if dependency A enables serde = { features = ["derive"] } and dependency B includes serde without features, Cargo activates the union for the entire compilation unit, preventing duplicate builds.

4. Monorepos & Workspace Inheritance

Similar to pnpm catalogs or npm workspaces, Cargo workspaces allow defining dependency versions centrally in the root Cargo.toml using [workspace.dependencies]. Member crates inherit them without version drift.

# Root Cargo.toml
[workspace]
resolver = "2"
members = ["crates/*", "services/*"]

[workspace.dependencies]
tokio = { version = "1.38", features = ["full"] }
serde = { version = "1.0", features = ["derive"] }
sqlx = { version = "0.7", features = ["runtime-tokio", "postgres", "uuid"] }
uuid = { version = "1.8", features = ["v4", "serde"] }

# services/user-service/Cargo.toml
[package]
name = "user-service"
version = "0.1.0"
edition = "2021"

[dependencies]
# Inherited directly from workspace root:
tokio = { workspace = true }
serde = { workspace = true }
sqlx = { workspace = true }
uuid = { workspace = true }

5. SemVer Differences: The 0.x & 0.0.x Pitfall

Node developers assume SemVer changes require a ^ or ~. In Cargo, bare strings are Caret requirements by default. Furthermore, the leftmost non-zero number designates the breaking major release boundary:

Requirement Resolved Version Range Cargo vs npm Behavior
"1.2.3" >= 1.2.3, < 2.0.0 Cargo implicitly adds ^. In npm, "1.2.3" is pinned unless written as "^1.2.3".
"0.2.3" >= 0.2.3, < 0.3.0 Minor is breaking! 0.2.4 is accepted, but 0.3.0 is rejected.
"0.0.3" >= 0.0.3, < 0.0.4 Patch is breaking! Only 0.0.3 is accepted; 0.0.4 breaks compilation.

6. Production Compilation: Profile Release Overrides

Unlike Node.js where bundlers (esbuild/webpack) perform tree-shaking, Rust binaries are optimized at the LLVM level. Configure your root Cargo.toml to strip debug symbols, enable Link-Time Optimization (LTO), and enforce single-codegen unit emission for peak binary density and microsecond execution:

# Root Cargo.toml
[profile.release]
opt-level = 3        # Maximum aggressive optimizations (default: 3)
lto = "thin"         # Cross-crate Link-Time Optimization with low build overhead
codegen-units = 1    # Disables parallel codegen for max cross-function inlining
panic = "abort"      # Strips unwind landing pads; slashes binary size by 15-25%
strip = true         # Automatically strips symbols & debuginfo (equivalent to `strip binary`)
