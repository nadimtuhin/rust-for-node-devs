Appendix 11 • Footguns

Top 10 Rust Footguns for Node Developers

Common misconceptions, memory traps, and async hazards when transitioning from dynamic JavaScript to systems Rust.

Footgun 1: Calling .clone() to appease the compiler

Calling .clone() duplicates heap memory. If you clone a large buffer on every HTTP request, your service will suffer worse latency than Node.js. Use borrowed references (&T) or zero-copy reference counting (Arc<T>) instead.

Footgun 2: Blocking the Tokio worker thread pool

Calling synchronous file I/O or std::thread::sleep inside an async function blocks the OS worker thread assigned to Tokio, starving hundreds of concurrent requests. Offload CPU-heavy or blocking work to tokio::task::spawn_blocking or use tokio::time::sleep.

Footgun 3: Unbuffered File and Socket I/O

In Node.js, stream buffers are automatic. In Rust, calling file.read() or socket.write() directly performs a separate kernel syscall for every call. Always wrap with BufReader and BufWriter to coalesce I/O operations into 8KB buffer blocks.

Footgun 4: Production .unwrap() & .expect() Panics

Calling .unwrap() on None or Err causes a thread panic. In Tokio worker tasks, an unhandled panic aborts the task. Use ? error propagation with anyhow for applications or thiserror for domain libraries.

Footgun 5: Cancellation Hazards in tokio::select!

When a branch completes in tokio::select!, other pending futures are immediately dropped. If a future is mid-stream on an AsyncReadExt::read_exact or AsyncWriteExt::write_all, partial bytes are lost unless the future is cancellation-safe. Prefer atomic or framed read operations.

Footgun 6: Holding std::sync::MutexGuard Across .await

Holding a std::sync::MutexGuard across an .await point makes the enclosing future !Send, preventing it from being spawned with tokio::spawn. Because Tokio uses a multi-threaded work-stealing scheduler, tasks can resume on a different OS thread, violating OS-level mutex invariants (unlocking a pthread_mutex_t from a different thread is undefined behavior or returns EPERM). Furthermore, keeping an OS mutex held while suspended can deadlock Tokio worker threads. Scope synchronous locks in tight blocks { let val = *lock; } or use tokio::sync::Mutex when locks must span async yields.

Footgun 7: Memory Leaks via Reference Cycles

Rust has no cycle-detecting garbage collector. Two structs holding Rc or Arc pointers to each other will never reach a reference count of 0, leaking memory forever. Break cycles with Weak<T> downgrade pointers.

Footgun 8: Silent Integer Overflow in --release Mode

In debug mode, integer overflow panics. In --release mode, Rust wraps arithmetic using two's complement for speed. For mission-critical calculations (financial transactions, indexing counters), use checked_add() or saturating_add().

Footgun 9: Self-Referential Structs & Pin Mechanics

JavaScript objects can freely reference other fields on themselves. In Rust, a struct cannot safely store a pointer or reference to another of its own fields because moving the struct (by returning it or passing by value) changes its memory address, turning internal pointers into dangling pointers. Rust uses Pin<P> to guarantee a value cannot move in memory before its destructor runs.

Footgun 10: Destructor Leaks via std::mem::forget & Thread Panics

Rust guarantees memory safety, but does NOT guarantee that destructors (the Drop trait) will always execute! Calling std::mem::forget(), encountering an aborting panic, or crashing inside an active process leaves file descriptors, socket locks, or temporary directory markers uncleaned on the system.
