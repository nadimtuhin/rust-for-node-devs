Appendix 11 • Footguns

Top 10 Rust Footguns for Node Developers

Common misconceptions, memory traps, and async hazards when transitioning from dynamic JavaScript to systems Rust.

Key takeaways

  • Blocking calls such as std::thread::sleep or std::fs inside async Rust stall every task scheduled on that Tokio worker thread; move them to tokio::task::spawn_blocking or use the async equivalents.
  • In Rust release builds, integer overflow wraps silently by default (overflow-checks is off in the release profile), while debug builds panic.
  • tokio::select! drops the branches that did not finish, so futures that are not cancellation safe, such as read_exact and write_all, can lose data.
  • Reference cycles of Rc or Arc leak memory because Rust has no tracing garbage collector; break them with Weak.
  • Running destructors is not guaranteed in Rust: std::mem::forget is a safe function, and panic = "abort" or std::process::exit skip Drop.

Footgun 1: Calling .clone() to appease the compiler

Calling .clone() on a String, Vec or similar type allocates and copies the whole heap buffer. Cloning a large buffer on every HTTP request adds an allocation and a memory copy proportional to its size, which can erase the performance you moved to Rust for. Pass borrowed references (&T) where you can, or share the data with Arc<T>, whose clone() only increments an atomic reference count and does not copy the data.

Footgun 2: Blocking the Tokio worker thread pool

Calling synchronous file I/O or std::thread::sleep inside an async function blocks the OS worker thread it runs on, so every other task queued on that worker waits until it returns. Use tokio::time::sleep and tokio::fs, move blocking calls into tokio::task::spawn_blocking, and send long CPU-bound work to a dedicated thread pool such as rayon, as the spawn_blocking docs recommend.

Footgun 3: Unbuffered File and Socket I/O

Node.js streams buffer for you. In Rust, each read() or write() on a File or TcpStream is a separate system call. When you do many small reads or writes (line-by-line parsing, writing small records), wrap the handle in BufReader or BufWriter, which batch them through an in-memory buffer (8 KiB by default on most platforms). Call flush() on a BufWriter before you rely on the data being written, because errors during the implicit flush on drop are ignored.

Footgun 4: Production .unwrap() & .expect() Panics

Calling .unwrap() on None or Err panics. A panic on the main thread ends the process. A panic inside a tokio::spawn task ends only that task, and its JoinHandle returns a JoinError, so a request can fail silently if nobody awaits the handle. With panic = "abort" in the profile, any panic ends the process. Propagate errors with ?, using anyhow in applications and thiserror for library error types.

Footgun 5: Cancellation Hazards in tokio::select!

When one branch of tokio::select! completes, the futures in the other branches are dropped. Tokio documents AsyncReadExt::read_exact, read_to_end, read_to_string and AsyncWriteExt::write_all as not cancellation safe: bytes already read or written are lost. In a select! loop, use cancellation-safe operations such as AsyncReadExt::read, mpsc::Receiver::recv, or StreamExt::next on a framed stream, or create the future once outside the loop and poll it by &mut reference.

Footgun 6: Holding std::sync::MutexGuard Across .await

std::sync::MutexGuard is !Send, because on some platforms the lock must be released by the thread that acquired it. Holding the guard across an .await makes the whole future !Send, so tokio::spawn rejects it at compile time. In futures that do not need Send, holding the guard across an .await can deadlock: another task on the same thread may try to take the lock while the holder is suspended. Copy what you need out in a tight scope, let val = { let guard = m.lock().unwrap(); guard.clone() };, or use tokio::sync::Mutex when the lock must span an .await. Clippy's await_holding_lock lint flags this pattern.

Footgun 7: Memory Leaks via Reference Cycles

Rust has no cycle-detecting garbage collector. Two values holding Rc or Arc pointers to each other never reach a strong count of 0, so neither is freed until the process exits. Break cycles by making one direction a Weak<T> (created with Rc::downgrade or Arc::downgrade), for example child-to-parent links in a tree.

Footgun 8: Silent Integer Overflow in --release Mode

In the default debug profile, integer overflow panics. In --release, overflow checks are off by default and arithmetic wraps using two's complement. When overflow matters (money, counters, index math), use checked_add(), saturating_add() or wrapping_add() to make the behavior explicit, or set overflow-checks = true under [profile.release].

Footgun 9: Self-Referential Structs & Pin Mechanics

JavaScript objects can freely reference their own fields. In safe Rust, a struct cannot hold a reference to one of its own fields, because moving the struct (returning it or passing it by value) changes its address and would leave that reference dangling. Async state machines need exactly this pattern, so Rust uses Pin<P>: once a value whose type is not Unpin is pinned, it is guaranteed not to move until it is dropped.

Footgun 10: Destructor Leaks via std::mem::forget & Aborts

Rust's memory safety guarantee does NOT include running destructors. std::mem::forget() is a safe function, and panic = "abort", std::process::exit() and signals such as SIGKILL all end the process without running Drop. The OS still reclaims memory and closes file descriptors, but state outside the process, such as temporary files, lock files and unflushed BufWriter data, is left behind.

Frequently asked questions

Is it bad to use .clone() everywhere in Rust?
Not always, but it costs an allocation and a copy for heap types like String and Vec. Cloning small values or Arc handles is cheap; cloning large buffers in a hot path is not. Prefer borrowing with &T and share large data with Arc<T>.
Why is my async Rust server slow when I call std::thread::sleep or read a file?
Those calls block the Tokio worker thread, so every other task on that worker stops making progress until they return. Use tokio::time::sleep and tokio::fs, or wrap blocking code in tokio::task::spawn_blocking. This is the Rust version of blocking the Node.js event loop with synchronous calls.
Does integer overflow crash a Rust program in production?
Not by default. Release builds disable overflow checks, so arithmetic wraps around silently, while debug builds panic. Use checked_*, saturating_* or wrapping_* methods, or enable overflow-checks = true in the release profile.
Can Rust leak memory?
Yes. Leaking memory is considered safe in Rust, so std::mem::forget, Box::leak and Rc or Arc reference cycles all leak without any unsafe code. Use Weak pointers to break cycles.
What happens when a spawned Tokio task panics?
With the default panic = "unwind", only that task stops, and awaiting its JoinHandle returns a JoinError whose is_panic() is true. The runtime and other tasks keep running. With panic = "abort", the whole process exits.
