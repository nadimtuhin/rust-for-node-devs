Senior Systems Interview Q&A

Memory layout, async, locking and unsafe questions that come up in senior Rust systems interviews, with answers grounded in the Rust docs.

Key takeaways

  • On a 64-bit target, String is 24 bytes on the stack (pointer, capacity, length) and &str is 16 bytes (pointer, length).
  • std::sync::MutexGuard is !Send, so a future that holds it across .await cannot be passed to tokio::spawn.
  • Local variables are dropped in reverse declaration order, while struct fields are dropped in declaration order.
  • unsafe does not disable the borrow checker; it only allows five extra operations, such as dereferencing raw pointers and calling unsafe functions.
  • Tokio's docs recommend std::sync::Mutex in async code for short critical sections, and tokio::sync::Mutex only when the guard must be held across .await.

Q1: What is the exact difference between String and &str in memory?

String is an owned, growable buffer of UTF-8 bytes stored on the heap. On a 64-bit target its stack footprint is 24 bytes: a pointer to the heap buffer, the capacity, and the current length. &str is a borrowed string slice of 16 bytes: a pointer to existing bytes and a length. A &str can point into a String's heap buffer, a stack array, or static data compiled into the binary (string literals are &'static str).

Q2: Why does holding std::sync::MutexGuard across an .await point fail to compile with tokio::spawn?

std::sync::MutexGuard does not implement Send, because on some platforms (for example pthread mutexes) the lock must be released by the thread that acquired it. A future that holds the guard across .await stores it in its state, which makes the future !Send. tokio::spawn requires Send futures because the multi-threaded scheduler may resume a task on a different worker thread, so the compiler rejects it. The code compiles if the future is never required to be Send, but it can then deadlock. The idiomatic fix is to drop the guard before the .await by scoping it in a block, or to use tokio::sync::Mutex or message passing.

Q3: What is Pin<&mut T> and why is it essential for async Rust?

Async functions compile into state machines. When a local reference lives across an .await point, the state machine stores both the value and a reference to it, making it a self-referential struct. If it moved in memory after that, the stored reference would dangle. Pin wraps a pointer and guarantees that a value whose type is not Unpin will not move again until it is dropped, which is why Future::poll takes self: Pin<&mut Self>.

Q4: When should you choose std::sync::Mutex vs tokio::sync::Mutex vs RwLock?

Use std::sync::Mutex for short in-memory critical sections that do not cross an .await; Tokio's shared-state tutorial says it is fine and often preferred in async code. Use tokio::sync::Mutex when the guard must be held across an .await, for example around an I/O resource; it is slower because locking is itself an async operation with a fair queue. Choose RwLock when reads clearly dominate and critical sections are long enough for parallel readers to matter. It does more bookkeeping than a Mutex, so measure before switching.

Additionally, std::sync::Mutex and std::sync::RwLock implement Lock Poisoning: if a thread panics while holding the lock, later calls return a PoisonError to warn about possibly corrupt state. tokio::sync::Mutex and parking_lot::Mutex do not poison on panic.

Q5: What is Rust's precise RAII drop order for variables and struct fields?

1. Local variables in a scope are dropped in reverse declaration order (last declared is dropped first).
2. Struct fields and tuple elements are dropped in declaration order (first field is dropped first).
3. Array and owned slice elements are dropped from the first element to the last.
4. A temporary is dropped at the end of its enclosing statement, and let _ = value; does not bind, so a temporary on the right side is dropped immediately.

Q6: What is a Fat Pointer in Rust and what are its memory dimensions?

A reference to a sized type (e.g. &i32 or &MyStruct) is 1 word (8 bytes on a 64-bit target) pointing directly to the data. A Fat Pointer to a dynamically sized type is 2 words (16 bytes): a data pointer plus metadata:
• Slices (&[T] or &str): the data pointer and the element count.
• Trait Objects (&dyn Trait): the data pointer and a vtable pointer. The vtable holds the concrete type's size, alignment, drop glue, and the trait's method pointers. Its exact layout is not a stable, documented ABI.

Q7: What is undefined behavior (UB) in Rust and does unsafe turn off the borrow checker?

No. An unsafe block does NOT turn off type checking or the borrow checker for references. The Rust Book lists five extra abilities it grants: dereferencing raw pointers, calling unsafe functions (including FFI), accessing or modifying mutable statics, implementing unsafe traits, and accessing fields of a union. Undefined behavior is any operation the language rules forbid, such as creating two live &mut references to the same data. The compiler optimizes on the assumption that UB never happens, so code containing UB can be miscompiled in ways that are hard to predict.

Frequently asked questions

What is the difference between String and &str in Rust?
String owns a growable heap buffer of UTF-8 bytes and is 24 bytes on the stack on 64-bit targets. &str is a borrowed view into UTF-8 bytes owned by something else and is 16 bytes. Take &str as a function parameter when you only need to read text.
Should I use std::sync::Mutex or tokio::sync::Mutex in async Rust?
Use std::sync::Mutex unless you must hold the lock across an .await. Tokio's own tutorial recommends the standard mutex for short critical sections because it is cheaper. Use tokio::sync::Mutex only when the guard has to live across an .await.
Does unsafe Rust disable the borrow checker?
No. The borrow checker still checks all references inside an unsafe block. unsafe only allows five extra operations, including dereferencing raw pointers and calling unsafe functions, and you become responsible for upholding the rules the compiler cannot check for those operations.
In what order does Rust drop variables and struct fields?
Local variables are dropped in reverse order of declaration when their scope ends. Struct fields, tuple elements and array elements are dropped in forward order. The Rust Reference chapter on destructors defines these rules.
Why do Rust futures need Pin?
An async function's state machine can hold references to its own fields across .await points, so moving it after polling starts would leave those references dangling. Pin guarantees a non-Unpin value stays at one address until it is dropped, which is why Future::poll takes Pin<&mut Self>.
