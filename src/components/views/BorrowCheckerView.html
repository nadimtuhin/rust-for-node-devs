Appendix 01 • Core Mental Model

Mastering the Rust Borrow Checker

Aliasing XOR Mutability, Non-Lexical Lifetimes (NLL), and how the borrow checker rules out data races in safe Rust at compile time.

Key takeaways

  • Rust's borrow checker allows either any number of shared references (&T) or exactly one mutable reference (&mut T) to a value at a time, never both.
  • Since Rust 1.31 (December 2018), Non-Lexical Lifetimes (RFC 2094) end a borrow at its last use instead of at the closing brace of its scope.
  • Polonius is the next borrow checker; it accepts some correct programs that NLL rejects, but it is still nightly-only (-Zpolonius) and its stabilization is a 2026 Rust project goal.
  • Shared references implement Copy and mutable references do not, so let r2 = r1; moves an &mut T while passing it to a function parameter typed &mut T reborrows it.
  • When ownership rules are too strict for a design, Rc<RefCell<T>> (single thread) and Arc<Mutex<T>> (multi-thread) move the aliasing check from compile time to run time.

1. The Golden Rule: Aliasing XOR Mutability

In JavaScript, object references are shared without restrictions. If three functions hold a reference to the same object, any of them can mutate it at any time. In single-threaded Node.js this shows up as hard-to-trace state mutation bugs. With shared memory across threads (for example SharedArrayBuffer in worker threads), unsynchronized access becomes a data race. Safe Rust rules data races out at compile time.

At any given time, for any value of type T, you can have:
• Any number of shared references (&T) OR
• Exactly one mutable reference (&mut T),
NEVER BOTH AT THE SAME TIME.

2. Non-Lexical Lifetimes (NLL) & Polonius

Before NLL, borrows were lexical: a borrow stayed active until the closing curly brace } of its enclosing scope. NLL (RFC 2094) shipped in Rust 1.31 for the 2018 edition and in Rust 1.36 for the 2015 edition. It computes borrows over the MIR control-flow graph, so a borrow ends at its last use.

let mut data = vec![1, 2, 3];

let first = &data[0];               // Shared borrow begins
println!("First item: {}", first);  // Last use of `first`: under NLL the borrow ends here

data.push(4);                       // Accepted under NLL; the old lexical checker rejected it

The Next Frontier: Polonius (Origin-Based Analysis)

NLL still rejects some correct code, most famously a conditional return of a borrow (listed as "problem case #3" in RFC 2094). Polonius is a reformulation of the borrow checker that tracks where each loan can flow (its "origins") statically, per program point. It is available on nightly with -Zpolonius and is not yet on stable; stabilizing "Polonius Alpha" is a 2026 Rust project goal. 

use std::collections::HashMap;

// Rejected by NLL (E0502), accepted under Polonius:
fn get_or_insert<'a>(map: &'a mut HashMap<String, String>, key: &str) -> &'a String {
    if let Some(v) = map.get(key) {
        return v; // Returning `v` forces this borrow to last for all of 'a, even on the path below
    }
    map.insert(key.to_string(), String::from("default")); // NLL: cannot borrow `*map` as mutable
    &map[key]
}

On stable today, work around it with the entry API: map.entry(key.to_string()).or_insert_with(|| String::from("default")).

3. Reborrowing vs. Move Semantics

Shared references (&T) implement Copy; mutable references (&mut T) do not. Moving an &mut T makes the source variable unusable. However, when the target type is already known to be &mut T (a function parameter, or a let with an explicit type), the compiler inserts an implicit reborrow instead of a move.

Move of a Mutable Reference

An untyped let moves the reference itself:

let mut s = String::from("hi");
let r1 = &mut s;
let r2 = r1; // MOVES r1 into r2

// println!("{}", r1);
// ERROR: borrow of moved value: `r1`
println!("{}", r2); // OK
Reborrowing (&mut *r)

Creates a shorter child borrow that suspends the parent:

let mut s = String::from("hi");
let r1 = &mut s;

// Explicit reborrow:
let r2 = &mut *r1; // r1 suspended while r2 is in use
r2.push_str(" world");

println!("{}", r1); // OK: r2 is no longer used

4. Escape Hatches & Smart Pointers

Frequently asked questions

Why does Rust say "cannot borrow as mutable because it is also borrowed as immutable"?
Error E0502 means a shared reference is still used later in the code while you try to take a mutable one. Rust allows many shared references or one mutable reference to a value, never both at once. Move the last use of the shared reference before the mutation, or clone the data you need from it.
Does Rust have a garbage collector like Node.js?
No, Rust has no tracing garbage collector. Each value has one owner and is dropped when that owner goes out of scope, and the borrow checker proves at compile time that no reference outlives the value. Reference counting with Rc or Arc is available when you need shared ownership.
What are non-lexical lifetimes in Rust?
Non-lexical lifetimes (NLL, RFC 2094) end a borrow at its last use instead of at the end of its enclosing block. NLL became the default in Rust 1.31 for the 2018 edition and in Rust 1.36 for the 2015 edition. It removed many false borrow errors that the older lexical checker reported.
Is Polonius available on stable Rust?
Not yet. Polonius can be enabled on nightly with -Zpolonius, and stabilizing its "alpha" form is a 2026 Rust project goal. On stable, rewrite code that needs it, for example using the HashMap entry API for get-or-insert.
How do I share mutable state between functions in Rust like a JavaScript object?
Use Rc<RefCell<T>> on one thread or Arc<Mutex<T>> across threads. Both let several owners mutate the same value, with the exclusive-access rule checked at run time instead of compile time. RefCell panics on a conflicting borrow, while Mutex blocks until the lock is free.
