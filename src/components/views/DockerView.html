Appendix 05 • Containerization

Production Multi-Stage Dockerfile & Binary Optimization

Build static binaries with cargo-chef caching, symbol stripping, MUSL cross-compilation, and distroless/scratch runtime containers.

1. The Gold-Standard Multi-Stage Dockerfile (with Stripping)

Using cargo-chef for layer caching and explicitly stripping unneeded debug symbols in the builder stage before packaging into Google Distroless:

# Stage 1: Dependency Chef Base
FROM rust:1.84-bookworm AS chef
RUN cargo install cargo-chef
WORKDIR /app

# Stage 2: Prepare lockfile recipe
FROM chef AS planner
COPY . .
RUN cargo chef prepare --recipe-path recipe.json

# Stage 3: Build & strip binary
FROM chef AS builder
COPY --from=planner /app/recipe.json recipe.json
RUN cargo chef cook --release --recipe-path recipe.json
COPY . .
RUN cargo build --release --bin server
# Explicit symbol stripping (cuts binary size by 40-70%)
RUN strip /app/target/release/server

# Stage 4: Ultra-minimal production runtime (< 20MB)
FROM gcr.io/distroless/cc-debian12:nonroot
WORKDIR /app
COPY --from=builder /app/target/release/server /app/server
USER nonroot:nonroot
EXPOSE 3000
ENTRYPOINT ["/app/server"]

2. Declarative Stripping in Cargo.toml

Instead of invoking the external strip utility in Docker, you can instruct rustc and LLVM to strip symbols and enable link-time optimization directly via [profile.release]:

# Cargo.toml
[profile.release]
opt-level = 3          # Max performance (use "z" or "s" if optimizing strictly for size)
lto = true             # Enable full Link-Time Optimization across crates
codegen-units = 1      # Maximize LTO optimization scope at the cost of compile time
strip = true           # Automatically strip symbols and debuginfo from the output binary
panic = "abort"        # Drops unwinding tables, significantly shrinking binary overhead

3. Zero-Dependency Containers with MUSL (FROM scratch)

Standard builds dynamically link to GNU libc (glibc). By cross-compiling against MUSL libc, you generate a 100% statically linked executable that can run in a completely empty scratch container with zero OS dependencies.

Common Target Triplets:

  • x86_64-unknown-linux-musl — 64-bit Linux (Intel/AMD)
  • aarch64-unknown-linux-musl — 64-bit Linux (ARM64 / AWS Graviton / Apple Silicon Docker)

MUSL multi-stage Dockerfile:

# Build statically linked binary with musl target
FROM rust:1.84-alpine AS builder
RUN apk add --no-cache musl-dev
WORKDIR /app

# Add the appropriate MUSL target triplet
RUN rustup target add x86_64-unknown-linux-musl

COPY Cargo.toml Cargo.lock ./
COPY src ./src
RUN cargo build --release --target x86_64-unknown-linux-musl --bin server

# Deploy into a true zero-overhead image (< 10MB)
FROM scratch
COPY --from=builder /app/target/x86_64-unknown-linux-musl/release/server /server
EXPOSE 3000
ENTRYPOINT ["/server"]
Note on OpenSSL & TLS: If your binary makes HTTPS requests, pure static MUSL builds require bundled certificates or pure-Rust TLS implementations (use rustls instead of native-tls / openssl).
