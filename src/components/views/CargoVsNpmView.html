Appendix 03 • Package Management

Cargo vs npm / pnpm

Additive feature flags, duplicate dependency handling without node_modules, workspace inheritance, pre-1.0 SemVer rules, and release profiles.

Key takeaways

  • Cargo is the Rust build tool and package manager in one: cargo add, cargo check, cargo build --release, cargo test and cargo clippy cover what npm scripts, tsc, a bundler, a test runner and ESLint do in a Node.js project.
  • Cargo resolves all SemVer-compatible requirements for a crate to one version, and builds two copies of a crate only when the requirements are SemVer-incompatible, such as 0.9 and 1.0.
  • Cargo features are additive: when several crates in the dependency graph enable different features of the same dependency, Cargo compiles that dependency once with the union of those features.
  • In Cargo.toml a bare version such as "0.2.3" means the caret range ^0.2.3, which allows 0.2.x updates but not 0.3.0, while the same string in package.json pins an exact version.
  • Release builds already use opt-level = 3; lto, codegen-units = 1, strip and panic = "abort" trade longer compile times or different panic behaviour for smaller or faster binaries.

2. How Cargo Solves the node_modules Problem

In Node.js, conflicting version ranges are resolved by nesting extra copies of a package inside node_modules, so the same package can be installed and loaded several times. Cargo has no node_modules: crate sources live in the shared ~/.cargo/registry cache and compiled artifacts go to the project's target/ directory. The resolver picks a single version for all SemVer-compatible requirements (for example ^1.0.100 and ^1.0.190 resolve to one 1.0.x). Only SemVer-incompatible requirements (e.g. serde 1.0 and serde 0.9) produce two copies, which are linked side by side with distinct mangled symbols.

The catch: types from the two copies are different types. Passing a value built with serde 0.9 where serde 1.0 traits are expected fails to compile with a confusing "expected X, found X" error. cargo tree --duplicates (cargo tree -d) lists every crate built more than once, similar to npm ls <pkg>.

3. Additive Feature Flags & Opt-Out (default-features = false)

In Rust, crate capabilities are gated behind compile-time feature flags. Features are additive: if crate A depends on serde with features = ["derive"] and crate B depends on it without, Cargo compiles serde once with the union of both feature sets. With resolver version 2 or later (the default since edition 2021), features enabled only by build-dependencies, proc-macros, dev-dependencies or other target platforms are not merged into your normal build. To drop features you don't need, declare default-features = false and list the ones you want:

[dependencies]
# reqwest 0.13 defaults: default-tls (rustls), charset, http2, system-proxy.
# Keep only rustls TLS and the JSON helpers:
reqwest = { version = "0.13", default-features = false, features = ["rustls", "json"] }
# no_std use: drop the default "std" feature, keep heap types:
serde = { version = "1.0", default-features = false, features = ["alloc"] }

4. Cargo Workspaces & Dependency Inheritance

Similar to pnpm workspaces, Cargo workspaces manage multiple crates with one shared Cargo.lock and one target/ directory. Versions declared once in [workspace.dependencies] are inherited with workspace = true:

# Root Cargo.toml
[workspace]
members = ["crates/api", "crates/auth", "crates/db"]
resolver = "3"   # edition 2024 default (Rust 1.84+); a virtual workspace without it falls back to "1"

[workspace.dependencies]
tokio = { version = "1", features = ["full"] }
serde = { version = "1.0", features = ["derive"] }
tracing = "0.1"

# crates/api/Cargo.toml
[dependencies]
tokio = { workspace = true }
serde = { workspace = true }

5. SemVer Quirks: Pre-1.0 Versions in Cargo vs npm

Cargo's caret rules for 0.x match npm's ^ rules. The difference for Node.js engineers is the default: in Cargo.toml a bare "0.2.3" means ^0.2.3, while a bare "0.2.3" in package.json is an exact pin. Write "=0.2.3" for an exact pin in Cargo. Ranges per The Cargo Book, "Specifying Dependencies":

Declared Version Cargo Permitted Range Breaking Change Point
"1.2.3" (or "^1.2.3") >= 1.2.3, < 2.0.0 Bump to 2.0.0
"0.2.3" >= 0.2.3, < 0.3.0 Bump to 0.3.0: minor bumps are breaking in 0.x
"0.0.3" >= 0.0.3, < 0.0.4 Bump to 0.0.4: every patch bump is breaking in 0.0.x

6. Production Build Profiles & LTO Optimization

In Node.js, minification with esbuild/terser trims bundle size. In Rust, [profile.release] in Cargo.toml controls optimization level, cross-crate inlining (LTO) and symbol stripping. cargo build --release already uses opt-level = 3, and since Rust 1.77 it strips debuginfo by default when debug is off. The settings below can shrink the binary further at the cost of compile time; measure the effect on your own crate with ls -lh target/release/<bin>:

[profile.release]
opt-level = 3        # Already the release default; "s" or "z" optimize for size
lto = "thin"         # Link-Time Optimization across crates ("fat" / true: slower, more thorough)
codegen-units = 1    # One codegen unit: slower compile, more inlining opportunities
panic = "abort"      # No unwinding tables; a panic in any thread or Tokio task ends the process
strip = true         # Strip symbols as well as debuginfo (same as "symbols")

Frequently asked questions

What is the Cargo equivalent of npm install?
cargo add <crate> adds a dependency to Cargo.toml, like npm install <pkg>. A fresh clone needs no separate install step: cargo build or cargo check downloads and compiles everything listed in Cargo.toml and Cargo.lock. cargo install <crate> is for command-line tools, similar to npm install -g.
Does Rust have a node_modules folder?
No. Cargo downloads crate sources into a shared cache under ~/.cargo/registry and writes compiled output to the project's target/ directory. Rust dependencies are statically linked into the final binary by default, so the binary is the only build artifact that needs to ship.
Should I commit Cargo.lock like package-lock.json?
Yes. The Cargo Book recommends committing Cargo.lock for applications and, since 2023, for libraries as well. Cargo ignores a library's lockfile when that library is used as a dependency, the same way npm ignores a dependency's package-lock.json.
Why doesn't cargo update move my 0.x dependency to the next minor version?
Cargo treats 0.2 to 0.3 as a breaking change. A requirement of "0.2.3" means >=0.2.3, <0.3.0, so cargo update stays within 0.2.x. Change the version in Cargo.toml, or run cargo add <crate>@0.3, to move to the next minor release.
What are Cargo features compared to optional npm packages?
Cargo features are compile-time switches declared by a crate that turn on optional code and optional dependencies. They are additive: Cargo compiles each dependency once with the union of features requested anywhere in the graph. npm has no direct equivalent; the closest patterns are optional peer dependencies and separate entry points.
