Appendix 01 • Core Mental Model

Mastering the Rust Borrow Checker

Aliasing XOR Mutability, Non-Lexical Lifetimes (NLL), and why the borrow checker prevents data races at compile time.

1. The Golden Rule: Aliasing XOR Mutability

In JavaScript, references are shared everywhere without restrictions. If three functions hold a reference to the same object, any of them can mutate it at any time. In single-threaded Node.js, this causes hard-to-trace state mutation bugs. In multi-threaded systems, it causes fatal data races.

At any given time, for any resource T, you can have:
• Multiple immutable references (&T) OR
• Exactly one mutable reference (&mut T),
NEVER BOTH AT THE SAME TIME.

2. Non-Lexical Lifetimes (NLL) & Polonius

Historically (pre-Rust 2018), lifetimes were strictly lexical: a borrow remained active until the closing curly brace } of its enclosing AST block. Rust 2018 introduced NLL (Non-Lexical Lifetimes), which calculates borrows over the Control Flow Graph (CFG) so that a borrow ends at its last point of usage.

let mut data = vec![1, 2, 3];

let first = &data[0];               // Immutable borrow begins
println!("First item: {}", first);  // Last point of usage! Lexical borrow ends here under NLL.

data.push(4);                       // Valid under NLL (in Rust 2015, this failed until scope ended)

The Next Frontier: Polonius (Origin-Based Analysis)

Even NLL fails on conditional returns from map lookups because CFG borrows approximate lifetimes along whole control paths. Polonius is the next-generation borrow checker that tracks loans via origins dynamically across execution paths: 

// Classic pattern rejected by NLL, accepted under Polonius:
fn get_or_insert(map: &mut HashMap<String, String>, key: &str) -> &String {
    if let Some(v) = map.get(key) {
        return v; // Under NLL, this borrow persists into the 'else' branch!
    }
    map.insert(key.to_string(), String::from("default")); // NLL Error: cannot borrow mutably
    &map[key]
}

3. Reborrowing vs. Move Semantics

Unlike immutable references (&T) which implement Copy, mutable references (&mut T) do not implement Copy. Moving an &mut T invalidates the source variable. However, Rust transparently inserts a reborrow when passing or assigning a mutable reference.

Explicit Move (Ownership Transfer)

Passing an owned value moves it permanently:

let mut s = String::from("hi");
let r1 = &mut s;
let r2 = r1; // MOVES r1 into r2!

// println!("{}", r1); 
// ERROR: borrow of moved value: `r1`
println!("{}", r2); // OK
Reborrowing (&mut *r)

Creates a temporary child borrow that suspends the parent:

let mut s = String::from("hi");
let mut r1 = &mut s;

// Implicit or explicit reborrow:
let r2 = &mut *r1; // r1 suspended while r2 lives
r2.push_str(" world");

println!("{}", r1); // OK! r1 usable once r2's lifetime ends
