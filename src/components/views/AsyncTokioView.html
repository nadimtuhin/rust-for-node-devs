Appendix 02 • Concurrency Deep Dive

Node.js libuv vs Tokio Multi-Threaded Runtime

Understanding poll-based futures, work-stealing executors, and why async Rust achieves sub-millisecond p99 latencies.

🟢 Node.js (libuv)

  • Single-threaded: Javascript executes on exactly one thread.
  • Push-based: Callbacks pushed to microtask/macrotask queues.
  • Event loop blocking: Heavy CPU computations freeze all incoming HTTP requests.
  • Promises: Eager evaluation (starts executing immediately upon instantiation).

🦀 Rust (Tokio)

  • Multi-threaded: Work-stealing scheduler across all physical CPU cores.
  • Pull-based: Futures are polled only when awakened by Waker.
  • CPU isolation: CPU tasks run cleanly on tokio::task::spawn_blocking or Rayon.
  • Futures: Lazy evaluation (does nothing until polled with .await).

The Cardinal Rule of Tokio

NEVER CALL SYNCHRONOUS BLOCKING CODE INSIDE AN ASYNC FUNCTION!
std::thread::sleep or synchronous file I/O blocks the OS thread assigned to the Tokio worker, stalling hundreds of concurrent HTTP futures!

Always use non-blocking equivalents: tokio::time::sleep and tokio::fs, or offload with tokio::task::spawn_blocking.
