Senior Systems Interview Q&A

Master the deep technical systems questions asked at Cloudflare, Discord, AWS, and Figma.

Q1: What is the exact difference between String and &str in memory?

String is an owned, growable vector of UTF-8 bytes stored on the heap. On a 64-bit CPU, its stack footprint is 24 bytes (pointer to heap buffer, capacity, and current length). In contrast, &str is a borrowed string slice consisting of only 16 bytes on the stack: a pointer to existing bytes and length. String slices can point to stack, heap, or static binary data (.rodata).

Q2: Why does holding std::sync::MutexGuard across an .await point fail to compile?

std::sync::MutexGuard explicitly does not implement the Send trait because OS-level mutexes (e.g. pthread mutexes) require the unlocking thread to be the identical thread that acquired the lock. Tokio's multi-threaded work-stealing scheduler can yield a task on Thread A and resume it on Thread B. The compiler rejects this at compile time. The idiomatic fix is scoping the synchronous lock to drop before the await, or using message-passing channels.

Q3: What is Pin<&mut T> and why is it essential for async Rust?

Async functions compile into state machines. When a future holds references across an .await point, it becomes a self-referential struct (fields pointing to other fields inside the same struct). If moved in memory, internal pointers become dangling pointers! Pin wraps a pointer to guarantee the underlying data will never move in memory before being dropped.

Q4: When should you choose std::sync::Mutex vs tokio::sync::Mutex vs RwLock?

Use std::sync::Mutex for short, uncontended in-memory operations that never yield across .await points (it avoids async allocation overhead). Use tokio::sync::Mutex ONLY when the lock guard must be held across an .await boundary. Choose RwLock only when reads vastly exceed writes (>90% reads) with non-trivial critical sections, otherwise the atomic state tracking overhead of RwLock will be slower than an uncontended Mutex.

Additionally, std::sync::Mutex and std::sync::RwLock implement Lock Poisoning (if a thread panics while holding the lock, subsequent calls return a PoisonError to protect against corrupt state), whereas tokio::sync::Mutex and parking_lot::Mutex intentionally do not poison on panic.

Q5: What is Rust's precise RAII drop order for variables and struct fields?

1. Local variables in a function scope are dropped in reverse declaration order (LIFO: last declared is dropped first).
2. Struct fields and tuple elements are dropped in declaration order (top-to-bottom: first field is dropped first).
3. Array and slice elements are dropped sequentially from index 0 to n-1.

Q6: What is a Fat Pointer in Rust and what are its memory dimensions?

A regular reference (e.g. &i32 or &MyStruct) is 1 word (8 bytes on 64-bit architecture) pointing directly to data. A Fat Pointer is 2 words (16 bytes) storing both a data pointer and runtime metadata:
• Slices (&[T] or &str): (data_ptr: *const T, len: usize).
• Trait Objects (&dyn Trait): (data_ptr: *const (), vtable_ptr: *const ()). The vtable contains the struct's size, alignment, destructor (drop glue), and function pointers for dynamic dispatch.

Q7: What is undefined behavior (UB) in Rust and does unsafe turn off the borrow checker?

No! The unsafe block does NOT turn off type checking or the borrow checker. It only grants 5 specific superpowers: dereferencing raw pointers, calling unsafe functions/FFI, implementing unsafe traits, mutating mutable static variables, and accessing fields of a union. Violating aliasing rules (e.g., creating overlapping &mut references) even inside unsafe triggers immediate Undefined Behavior, allowing LLVM optimizations to miscompile the binary.
