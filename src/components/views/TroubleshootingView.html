Appendix 09 • Diagnostics

Diagnostics, Flamegraphs & Profiling

Compilation flags, profiler setup, and step-by-step workflows for finding CPU hot spots, async stalls, heap churn and undefined behavior in Rust services.

Key takeaways

  • cargo flamegraph (install with cargo install flamegraph) records CPU stacks with perf on Linux and DTrace on macOS and writes an interactive flamegraph.svg.
  • Release builds need debug = true under [profile.release], or CARGO_PROFILE_RELEASE_DEBUG=true, so flamegraphs show function names instead of raw addresses.
  • Miri runs tests in an interpreter that detects many kinds of undefined behavior in unsafe code; install it with rustup +nightly component add miri and run cargo +nightly miri test.
  • tokio-console shows live per-task poll times and wakeups, but the service must be built with RUSTFLAGS="--cfg tokio_unstable" and must call console_subscriber::init().
  • The dhat crate swaps in a profiling global allocator and writes dhat-heap.json when its Profiler is dropped, which DHAT's online viewer can open.

Diagnostics & Profiling Rosetta Stone

How core Node.js diagnostic tooling maps directly to Rust systems profiling equivalents:

Diagnostic Goal Node.js Tooling Rust Equivalent
CPU Profiling / Flamegraphs 0x, clinic flame, node --prof cargo flamegraph (perf / DTrace)
Event Loop / Async Starvation clinic bubbleprof, event-loop-lag tokio-console (Task tracing subscriber)
Heap Allocations & Churn Chrome DevTools Heap Snapshot, clinic heapprofiler dhat-rs, Valgrind massif
Memory Safety & UB N/A (Managed VM) / ASan for C++ Addons cargo +nightly miri (MIR interpreter)

1. CPU Flamegraph Profiling (cargo-flamegraph)

Generates interactive SVG call graphs (like 0x or clinic flame in Node). Profile a release build with debug info enabled, otherwise inlined frames show as addresses. You can also set CARGO_PROFILE_RELEASE_DEBUG=true for a single run instead of editing Cargo.toml.

Cargo.toml configuration:

[profile.release]
debug = true       # Retain DWARF symbols for function names (line numbers & symbols)
strip = false      # Do not strip symbol tables

Execution commands (use --root instead of running sudo cargo to avoid target/ permission corruption):

# Installation
cargo install flamegraph

# macOS (uses DTrace under the hood; --root elevates DTrace safely):
cargo flamegraph --root --bin my-service -- --port 8080

# Linux (uses perf; ensure perf events are unlocked or pass --root):
sudo sysctl -w kernel.perf_event_paranoid=-1
cargo flamegraph --bin my-service -- --port 8080

# Profile specific benchmark or integration test:
cargo flamegraph --test integration_tests -- test_throughput

2. Undefined Behavior Detection (cargo miri)

Miri interprets Rust's Mid-level Intermediate Representation (MIR) and reports undefined behavior it observes while running your tests: out-of-bounds and use-after-free accesses, invalid values, aliasing violations, data races, and memory leaks. It only checks code paths your tests execute, runs much slower than native code, and cannot execute most FFI calls, so keep Miri test cases small.

# Install nightly toolchain & Miri component
rustup +nightly component add miri

# Run test suite under Miri using toolchain override without polluting global default:
cargo +nightly miri test

# Run a specific binary:
cargo +nightly miri run --bin my-service

# Extra checks: Tree Borrows aliasing model, strict provenance, symbolic alignment:
MIRIFLAGS="-Zmiri-tree-borrows -Zmiri-strict-provenance -Zmiri-symbolic-alignment-check" cargo +nightly miri test

# Allow tests that read env vars, files or the clock (Miri isolates them by default):
MIRIFLAGS="-Zmiri-disable-isolation" cargo +nightly miri test

3. Real-Time Async Task Tracing (tokio-console)

Inspect task scheduling starvation, blocked async worker threads, and channel backpressure live (equivalent to Node.js event-loop lag inspection and clinic bubbleprof).

// 1. Cargo.toml dependency:
// [dependencies]
// console-subscriber = "0.5"
// tokio = { version = "1", features = ["full", "tracing"] }

// 2. In src/main.rs: initialize before spawning the tasks you want to inspect.
fn main() -> Result<(), Box<dyn std::error::Error>> {
    // Sets the global tracing subscriber and serves gRPC on 127.0.0.1:6669
    // (override with TOKIO_CONSOLE_BIND) from its own background thread
    console_subscriber::init();

    tokio::runtime::Builder::new_multi_thread()
        .enable_all()
        .build()?
        .block_on(async {
            // ... rest of async service
            Ok(())
        })
}
# 3. Compile service with Tokio unstable flags enabled:
RUSTFLAGS="--cfg tokio_unstable" cargo run

# 4. In a separate terminal, launch the console TUI:
cargo install --locked tokio-console
tokio-console http://127.0.0.1:6669

4. Memory Allocation & Heap Profiling (DHAT & Valgrind)

Track heap churn, short-lived allocations, and memory leaks down to the allocating stack frame. DHAT works on every platform because it lives inside your binary; Valgrind Massif needs Linux (or another Valgrind-supported OS) but requires no code changes.

// 1. Cargo.toml:
// [dependencies]
// dhat = { version = "0.3", optional = true }
// [features]
// dhat-heap = ["dep:dhat"]

// 2. In src/main.rs:
#[cfg(feature = "dhat-heap")]
#[global_allocator]
static ALLOC: dhat::Alloc = dhat::Alloc;

fn main() {
    #[cfg(feature = "dhat-heap")]
    let _profiler = dhat::Profiler::new_heap();

    // Application logic...
    // Writes `dhat-heap.json` when `_profiler` is dropped at the end of main
    // (not on std::process::exit or an aborting panic)
}

DHAT Profiling execution & inspection:

# Run binary with dhat-heap feature and release debug symbols:
cargo run --release --features dhat-heap

# Visualize results in the interactive DHAT web viewer:
# Open https://nnethercote.github.io/dh_view/dh_view.html and load `dhat-heap.json`
# Linux Valgrind Massif (Full Process Heap Profiler):
valgrind --tool=massif --pages-as-heap=yes --massif-out-file=massif.out target/release/my-service
ms_print massif.out

Frequently asked questions

What is the Rust equivalent of clinic flame or 0x?
cargo flamegraph from the flamegraph-rs project is the closest equivalent. Install it with cargo install flamegraph and run cargo flamegraph --bin <name>; it uses perf on Linux and DTrace on macOS and writes flamegraph.svg. Enable debug = true in [profile.release] so frames have names.
Why does my Rust flamegraph show hex addresses instead of function names?
The release profile does not include debug info by default, so the profiler has no symbol data for many frames. Add debug = true under [profile.release] or run with CARGO_PROFILE_RELEASE_DEBUG=true, and do not set strip = true for profiling builds.
How do I find what is blocking the Tokio runtime, like event loop lag in Node.js?
Use tokio-console. Add the console-subscriber crate, call console_subscriber::init(), build with RUSTFLAGS="--cfg tokio_unstable", then run the tokio-console TUI. Tasks with long poll times are usually doing blocking or CPU-heavy work that belongs in spawn_blocking.
How do I check unsafe Rust code for undefined behavior?
Run your tests under Miri with cargo +nightly miri test after installing it with rustup +nightly component add miri. Miri reports undefined behavior on the code paths the tests execute, such as use-after-free, out-of-bounds access and aliasing violations. Pass extra options through the MIRIFLAGS environment variable.
How do I take a heap profile of a Rust program, like a Chrome heap snapshot?
Use the dhat crate: install dhat::Alloc as the global allocator behind a Cargo feature, create dhat::Profiler::new_heap() at the start of main, and open the resulting dhat-heap.json in DHAT's viewer. On Linux, Valgrind's Massif tool profiles the heap without code changes.
