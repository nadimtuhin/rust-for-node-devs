Appendix 01 • Core Mental Model

Mastering the Rust Borrow Checker

How to reason about Aliasing XOR Mutability, Non-Lexical Lifetimes (NLL), and why the borrow checker is your pair programmer.

1. The Golden Rule: Aliasing XOR Mutability

In JavaScript, references are shared everywhere without restrictions. If three functions hold a reference to the same object, any of them can mutate it at any time. In single-threaded Node.js, this causes hard-to-trace bugs. In multi-threaded systems, it causes fatal data races.

Rust enforces a fundamental mathematical axiom at compile time:

At any given time, for any resource T, you can have:
• Multiple immutable references (&T) OR
• Exactly one mutable reference (&mut T),
NEVER BOTH AT THE SAME TIME.

2. Non-Lexical Lifetimes (NLL)

In early versions of Rust, a reference lived until the end of its enclosing curly brace scope }. Since Rust 2018, the compiler uses Non-Lexical Lifetimes (NLL): a borrow ends at its last point of usage.

let mut data = vec![1, 2, 3];

let first = &data[0]; // Immutable borrow begins
println!("First item: {}", first); // Last point of usage! Immutable borrow ends here.

data.push(4); // Perfectly valid under NLL! No error.

3. Escape Hatches when Ownership isn't Tree-shaped
