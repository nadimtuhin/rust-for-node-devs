Appendix 02 • Concurrency Deep Dive

Node.js libuv vs Tokio Multi-Threaded Runtime

Understanding poll-based futures, work-stealing executors, cooperative scheduling, and cancellation safety in async Rust.

Key takeaways

  • Node.js runs all JavaScript on one thread, while Tokio's default multi-thread runtime runs async tasks on one worker thread per CPU core and moves tasks between workers by work-stealing.
  • Rust futures are lazy: nothing runs until the future is awaited or spawned, unlike a JavaScript Promise whose executor runs immediately.
  • Blocking calls such as std::thread::sleep inside an async task stall every other task on that worker thread; use tokio::time::sleep, tokio::fs, or tokio::task::spawn_blocking instead.
  • Tokio gives each task a budget of 128 operations per scheduling tick on its own sockets, timers and channels, but a CPU loop with no .await never yields.
  • tokio::select! drops the branches that lose, so only cancellation-safe operations such as mpsc::Receiver::recv are safe to race in a loop.

🟢 Node.js (libuv + V8)

  • Single-threaded JS Engine: User JavaScript executes on one V8 thread (per isolate; worker threads get their own).
  • libuv Threadpool: File I/O, dns.lookup, and some async crypto (e.g. pbkdf2, scrypt) run on a pool that defaults to 4 threads (UV_THREADPOOL_SIZE).
  • Callback Queues: Resolved Promises queue microtasks; timers and I/O callbacks run in the event loop phases.
  • Event loop starvation: CPU-heavy work on the main thread blocks all HTTP routing and I/O handlers until it finishes.
  • Eager Promises: A Promise's executor runs synchronously the moment the Promise is created.

🦀 Rust (Tokio)

  • Work-Stealing Multi-Threading: By default one worker thread per CPU core; idle workers steal queued tasks from busy ones (see Tokio's 2019 post "Making the Tokio scheduler 10x faster").
  • OS I/O Multiplexing: Non-blocking network I/O driven by mio (epoll on Linux, kqueue on macOS, IOCP on Windows).
  • Pull-based Futures: Futures are lazy state machines; the executor polls them, and a Waker tells it when a pending future is ready to be polled again.
  • Separate Blocking Pool: tokio::task::spawn_blocking runs blocking work on a separate pool (default cap 512 threads). tokio::fs uses this pool internally.
  • Task Budgets: Tokio's own resources make a task yield after 128 operations per tick so one busy task cannot hog a worker.

The Cardinal Rule of Tokio

Do not call synchronous blocking code inside an async function.
std::thread::sleep or synchronous file I/O blocks the OS thread running the Tokio worker, so every other task queued on that worker waits until the call returns.

Use non-blocking equivalents (tokio::time::sleep, tokio::fs) or offload with tokio::task::spawn_blocking. Runtime shape is set on the entry point:

// Multi-thread runtime pinned to 4 workers (the default is one worker per CPU core)
#[tokio::main(flavor = "multi_thread", worker_threads = 4)]
async fn main() {
    let hash = tokio::task::spawn_blocking(|| expensive_hash(b"password"))
        .await
        .expect("blocking task panicked");
    println!("{hash}");
}

// Single-threaded alternative, closest to Node's model:
// #[tokio::main(flavor = "current_thread")]

Cooperative Multitasking & tokio::task::yield_now()

Node.js developers use setImmediate() to break up long-running loops so the event loop can service I/O. Tokio tasks are also cooperative: there is no preemption, and a task only gives up its worker thread at an .await that returns Pending. A tight CPU loop without such a point starves other tasks on the same worker.

The Solution: Call tokio::task::yield_now().await inside long-running async loops. This returns control to the scheduler, which re-queues the current task behind other pending tasks. 
use tokio::task;

async fn process_large_dataset(chunks: Vec<Chunk>) {
    for (i, chunk) in chunks.into_iter().enumerate() {
        process_chunk(chunk);

        // Cooperatively yield every 100 iterations:
        if i % 100 == 99 {
            task::yield_now().await;
        }
    }
}

Note: Tokio's automatic co-op budget (128 operations per tick, introduced in Tokio 0.2.14) only applies to Tokio resources such as sockets, timers and channels. Plain CPU loops need manual yields, or better, spawn_blocking or a dedicated thread pool such as rayon for heavy compute.

tokio::select! & Cancellation Safety

In JavaScript, Promise.race([a, b]) lets the losing promise keep running in the background. In Tokio, tokio::select! uses drop-based cancellation: when one branch completes, the other branch futures are dropped, running their Drop code. Their work stops at whatever .await point they had reached.

Tokio's docs define a method as cancellation-safe if, when it is used as a branch of select! in a loop and another branch completes first, no data is lost.

Idiomatic Handling for Non-Cancellation-Safe Operations:

For operations like write_all, dropping the future midway leaves the stream partly written. Move the write into its own spawned task and race a channel against a CancellationToken (from tokio-util); the spawned task finishes the write even if you stop waiting:

use tokio::io::AsyncWriteExt;
use tokio_util::sync::CancellationToken;

let (tx, rx) = tokio::sync::oneshot::channel();
tokio::spawn(async move {
    let res = writer.write_all(&payload).await;
    let _ = tx.send(res);
});

tokio::select! {
    res = rx => { /* write finished: res is Result<io::Result<()>, RecvError> */ }
    _ = cancel_token.cancelled() => { /* stop waiting; the write is not torn midway */ }
}

Frequently asked questions

Is Tokio the Rust equivalent of the Node.js event loop?
Yes, Tokio plays the role of libuv: it drives I/O readiness from the OS and schedules async tasks. The difference is that Tokio's default runtime runs tasks on several worker threads at once, while Node runs all JavaScript on one thread. #[tokio::main(flavor = "current_thread")] gives a single-threaded runtime closer to Node's model.
Why does my Rust async function not run when I call it?
Rust futures are lazy, so calling an async function only builds a future and does nothing until it is awaited or passed to tokio::spawn. This differs from JavaScript, where a Promise starts work as soon as it is created. The compiler warns about unused futures with "futures do nothing unless you .await or poll them".
What happens if I call blocking code in a Tokio async function?
The blocking call occupies the worker thread, so every other task scheduled on that worker waits until it returns. Use async versions such as tokio::time::sleep and tokio::fs, or move the work to tokio::task::spawn_blocking, which runs it on a separate thread pool capped at 512 threads by default.
What is the Rust equivalent of Promise.race?
tokio::select! waits on several futures and runs the branch of the first one to finish. Unlike Promise.race, the losing futures are dropped and stop running. Only race cancellation-safe operations, such as mpsc::Receiver::recv, inside a loop.
What is the Rust equivalent of setImmediate for long loops?
tokio::task::yield_now().await hands control back to the Tokio scheduler so other tasks can run, then resumes the current task later. For heavy CPU work, spawn_blocking or a rayon thread pool is usually a better fit than sprinkling yields.
