Appendix 06 • Quality & Testing

Testing & Mocking: Jest / Vitest vs Rust

Unit tests, external integration tests, serial database testing, and trait mocking with mockall.

Key takeaways

  • Rust's test runner is built into Cargo: cargo test compiles and runs #[test] functions with no extra framework like Jest or Vitest.
  • Unit tests live in a #[cfg(test)] module inside the source file and can call private functions; integration tests live in tests/ and only see the crate's public API.
  • Each file directly under tests/ is compiled as its own crate, so shared helpers go in tests/common/mod.rs to avoid being run as a test file.
  • Tests within one test binary run in parallel threads by default; cargo test -- --test-threads=1 runs them one at a time, similar to jest --runInBand.
  • Rust has no runtime module patching like jest.mock(); you put dependencies behind a trait and let mockall generate a mock type at compile time.

1. Built-in Synchronous & Async Unit Tests

Unit tests live right inside your source files in a #[cfg(test)] module. They can access private functions and run in parallel threads by default. Async tests use #[tokio::test], which builds a fresh single-threaded (current_thread) runtime per test; use #[tokio::test(flavor = "multi_thread")] when the code under test needs multiple workers.

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_sync_math() {
        assert_eq!(2 + 2, 4);
    }

    #[tokio::test]
    async fn test_async_fetch() {
        let result = async_query_user(1).await;
        assert!(result.is_ok());
    }
}

2. External Integration Tests & Directory Convention

In Node.js, test runners search for *.test.ts anywhere. In Rust, Cargo compiles each file directly under tests/ as an independent external crate that links your library crate (src/lib.rs). A binary-only crate with just src/main.rs cannot be imported this way. To share fixtures without Cargo treating them as standalone tests, use the tests/common/mod.rs convention from The Rust Book:

my_project/
├── Cargo.toml
├── src/
│   ├── lib.rs
│   └── main.rs
└── tests/
    ├── common/
    │   └── mod.rs          # Shared fixture module (NOT compiled as a test binary)
    └── integration_test.rs # Root test crate (tests only public APIs)

Shared helper in tests/common/mod.rs:

// tests/common/mod.rs
pub fn setup_test_db() -> String {
    // Spin up test db or create temporary schema
    "postgres://localhost:5432/test_db".to_string()
}

Integration test in tests/integration_test.rs:

// tests/integration_test.rs
use my_project::app; // Imported as an external crate
mod common;

#[tokio::test]
async fn test_create_user_flow() {
    let db_url = common::setup_test_db();
    let response = app::run_migration(&db_url).await;
    assert!(response.is_ok());
}

3. Isolated Database Tests: --test-threads=1

Rust's built-in test harness runs the tests inside each test binary on multiple threads at once (by default one per available CPU). Cargo runs the separate test binaries (the lib, each tests/*.rs file) one after another. When tests share a database and truncate tables or depend on row counts, parallel tests inside one binary can clash and cause flaky failures.

To run tests serially in a single thread:

# Pass --test-threads to the test binary via Cargo
cargo test -- --test-threads=1

# Or run only integration tests serially:
cargo test --test integration_test -- --test-threads=1

# Alternatively, set the environment variable:
RUST_TEST_THREADS=1 cargo test
Node.js Comparison: In Jest, this is the equivalent of jest --runInBand; in Vitest, vitest --no-file-parallelism. In Rust, you can also use the serial_test crate (#[serial] attribute) to force only DB tests into serial execution while keeping pure unit tests parallel.

4. Mocking Traits with mockall

JavaScript allows runtime module replacement (jest.mock('./api'), vi.mock()). In Rust, dependencies are abstracted behind traits, and mockall generates a mock implementation of the trait at compile time. In real code, write #[cfg_attr(test, mockall::automock)] so the mock only exists in test builds.

#[mockall::automock]
pub trait UserRepository {
    fn get_user(&self, id: u32) -> Result<String, &'static str>;
}

#[test]
fn test_service_with_mock() {
    let mut mock = MockUserRepository::new();
    mock.expect_get_user()
        .with(mockall::predicate::eq(42))
        .returning(|_| Ok("Alice".to_string()));

    assert_eq!(mock.get_user(42).unwrap(), "Alice");
}

Frequently asked questions

What is the Rust equivalent of Jest or Vitest?
Rust's test harness is built into the compiler and Cargo, so cargo test replaces Jest or Vitest for most projects. Mark functions with #[test] and use assert!, assert_eq! and assert_ne! for assertions. Crates such as mockall, serial_test and the separate runner cargo-nextest add features on top.
Where do I put tests in a Rust project?
Put unit tests in a #[cfg(test)] mod tests block at the bottom of the source file they test, where they can reach private functions. Put integration tests in a top-level tests/ directory, where each file is compiled as a separate crate that can only use your library's public API.
How do I test async functions in Rust?
Annotate an async fn test with #[tokio::test], which creates a Tokio runtime for that test and awaits the body. The default runtime is single-threaded; use #[tokio::test(flavor = "multi_thread")] if the code needs several worker threads.
How do I run Rust tests one at a time like jest --runInBand?
Run cargo test -- --test-threads=1, or set RUST_TEST_THREADS=1. The flag goes after -- because it is passed to the test binary, not to Cargo. To serialize only some tests, mark them with #[serial] from the serial_test crate.
How do I mock a dependency in Rust like jest.mock?
Define the dependency as a trait, make your code accept any type implementing it, and add #[cfg_attr(test, mockall::automock)] to the trait. mockall then generates a MockYourTrait type where you set expectations with expect_method().returning(...). Rust cannot swap modules at run time the way jest.mock() does.
